기획 의도

실무에서 캠페인을 기획할 때 가장 자주 쓰는 건 화려한 프레임워크가 아니라, 목표·근거·전략·활동이 끊기지 않고 이어지는지 확인하는 습관이었습니다. 이 습관을 슬라이드나 문서가 아니라, 브라우저에서 바로 쓸 수 있는 도구로 옮기고 싶었습니다.

Think2Brief는 마케팅의 정답을 대신 골라주는 도구가 아닙니다. 지금 작성한 판단과 근거, 전략과 활동이 하나의 논리로 이어지는지를 점검하는 작업 공간입니다. 회원가입도, 외부 서버 전송도 없이 브라우저에만 저장되도록 만든 것도 같은 이유입니다 — 실무에서 바로, 가볍게 쓸 수 있어야 의미가 있었습니다.

산출물

질문 구조를 고르는 시작 화면부터 판단과 근거를 카드로 쌓는 작업 보드, 논리 연결을 점검하는 화면, 최종 브리프까지 — 실제 제품 화면입니다.

제작 방법

코드를 직접 작성하는 대신, 제품 구조와 요구사항을 설계하고 Claude Code와 Codex에게 구현을 맡긴 뒤 결과를 검토하는 방식으로 만들었습니다. 완성 후, 이 작업이 "바이브 코딩"인지 두 도구에게 그대로 물었습니다.

Claude
"바이브 코딩"이라 부르기는 어렵습니다. 판단 근거를 사람이 직접 정리해서 코드에 남긴 흔적, "예시가 논리 점검에서 경고를 내면 안 된다" 같은 실제 실패 시나리오를 검증하는 회귀 테스트, AI 리뷰어에게 넘길 때 미리 정해둔 검토 기준까지 — 정확히는 "AI로 구현하되 설계 판단과 검증은 본인이 직접 쥐고 있는 방식"입니다. 요즘 용어로는 vibe coding보다 AI-assisted engineering에 더 가깝습니다.
Codex
Karpathy가 처음 쓴 바이브 코딩은 diff도 거의 안 보고 결과 위주로 가는 방식에 가깝습니다. 이 기준으로 보면, 구현 방식은 바이브 코딩 계열이지만 개발 프로세스는 훨씬 통제된 AI-assisted development에 가깝습니다. 그러니 "바이브 코딩으로 만들었습니다"보다 "코드를 직접 작성하기보다 제품 구조와 요구사항을 설계하고, Claude Code와 Codex를 활용해 구현·검증했습니다"가 더 정확한 설명입니다.

평가

커밋 이력을 기준으로 정리했습니다.

실제 커밋 이력에는 완성된 결과물보다 다듬어가는 과정이 더 많이 남아 있습니다. 첫 커밋으로 제품과 개인정보 처리방침 사이트를 통째로 세운 뒤, 이어지는 커밋은 전부 손질이었습니다 — 목업 대신 실제 화면 스크린샷으로 교체하고, 카피 톤을 낮추고, 화면 캡션 순서를 다시 잡고, 아직 쓰지 않는 브라우저 저장 권한 문구를 지웠습니다.

이 흐름에서 드러나는 건 "한 번에 완성한 결과물"이 아니라 "실제로 켜 놓고 확인하며 고친 흔적"입니다. 특히 구현되지 않은 권한 문구를 뒤늦게라도 제거한 커밋은, 카피를 그대로 게시하지 않고 실제 배포된 확장 프로그램의 동작을 기준으로 사이트를 검증했다는 신호입니다.

물론 한계도 있습니다. 커밋 메시지만으로는 각 판단을 사람이 먼저 냈는지 AI가 먼저 제안했는지까지는 알 수 없습니다. 다만 적어도 이 프로젝트에 관해서는, "만들고 끝"이 아니라 "만들고 실제와 맞는지 검증"하는 루틴이 반복적으로 나타납니다.
